# 有效会议助手 · 使用说明

技术方向：Next.js（App Router）+ TypeScript + Tailwind；**纯客户端**，会议数据存浏览器 `localStorage`，无账号体系；覆盖判定默认由内置规则引擎完成，可选接入任意 OpenAI 兼容大模型做语义复核（fail-open，调用失败不阻断）。

---

## User Flow 1：新建会议与选模板

```Plain Text
┌──────────────────────────────────────────────────────────────────┐
│ 用户点击「新建会议」或首页「⚡ 一键体验示例会议」                      │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ 选择模板（4 选 1）                                                   │
│ - 产品上线决策会（含 6 分钟示例逐字稿）                               │
│ - 项目复盘会（含 5 分钟示例逐字稿）                                   │
│ - 客户推进会 / 管理层决策会（空白模板，可改目标与议程）               │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ 进入会前配置页（目标 / 议程 / 角色均可基于模板再编辑）                │
└──────────────────────────────────────────────────────────────────┘
```

用户看到什么

- 首页展示工具定位与「Mock 标识 / 已知限制」区块，评审点开即知哪些是真的、哪些是演示。
- 4 个模板，其中两个带预置示例逐字稿，可一键载入后「逐条推进」实时演示判定。

后台需要做什么

- 模板为前端静态配置（`lib/templates.ts`），无需服务端；所选模板写入当前会议对象。
- 示例会议通过 `?demo=launch` / `?demo=retro` 直达，便于评审与演示。

业务意义

模板降低录入成本，让评审从「产品上线决策会」这类真实场景直接体验目标达成度检查。

## User Flow 2：会前配置（目标 / 议程 / 角色）

```Plain Text
┌──────────────────────────────────────────────────────────────────┐
│ ① 会议目标                                                          │
│    四类：Key Goal / Conclusion / Decision / Action                  │
│    每项目标标注优先级：必须完成 / 建议完成 / 仅供记录                 │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ ② 议程结构                                                          │
│    模式：时间顺序 / 发言人顺序 / 环节推进 / 环节×发言人矩阵          │
│    每个环节可指定「必须发言的人」                                    │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ ③ 角色（参会人）                                                    │
│    姓名 + 职务；后续用于「谁该表态却没表态」的发言人矩阵判定          │
└──────────────────────────────────────────────────────────────────┘
```

用户逻辑

- 目标决定会后「是否达成」；优先级决定结束前缺口检查的严重程度（必须完成未覆盖 = 阻塞）。
- 环节×发言人矩阵让工具能指出「某环节、某关键人尚未表态」。

后台需要做什么

- 目标 / 议程 / 角色写入会议对象；优先级与环节必发言人是覆盖判定的输入。
- 不强制全部填写，但「必须完成」类目标为空会直接标记为缺口。

业务意义

会前把「本次会议要达成什么」显性化，是后续自动检查的前提；没有目标就没有「达成度」。

## User Flow 3：会中录入与覆盖检查（核心）

```Plain Text
┌──────────────────────────────────────────────────────────────────┐
│ 用户进入「会议中」页                                                 │
│ 录入方式（可混用）：                                                 │
│ - 手输：逐条添加发言（发言人 + 文本）                                │
│ - 批量粘贴：整段文字，按行解析                                        │
│ - 示例逐条推进：点「下一步」播放示例逐字稿，模拟实时会议              │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ 实时覆盖看板                                                         │
│ - 目标视图：每项目标 → 未覆盖 / 仅提及 / 已讨论 / 已达成(决策已拍板) │
│ - 议题视图：每个议程环节 → 已讨论 / 未讨论                           │
│ - 发言人视图：每个必发言人 → 已表态 / 尚未表态                       │
│ - 行动项视图：每个 Action → 有 owner+截止 / 缺 owner / 缺截止        │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ 会中主动提示（nudge）                                                │
│ 「销售负责人赵敏在决策环节尚未表态」「是否按期上线尚未拍板」…        │
└──────────────────────────────────────────────────────────────────┘
```

用户逻辑

- 录入讨论内容后，看板实时更新，颜色标注达成度；可随时在会中纠正遗漏。
- 主动提示帮助主持人现场追问，而不是会后才发现。

后台需要做什么

- 规则引擎（`lib/engine.ts`）做关键词匹配、决策/行动信号词识别、owner + 截止抽取、环节×发言人矩阵判定。
- 所有判定为确定性规则（不依赖 LLM），无 Key 也能 100% 跑通。
- 可选「AI 语义复核」按钮：把目标与逐字稿发给模型再判一遍，结果以 `AI` 徽章叠加显示，不影响规则结论。

业务意义

把「为了达成目标还差什么」从主持人脑海里搬到了实时看板，避免会议散场才发现关键决策没拍板。

## User Flow 4：结束前缺口检查

```Plain Text
┌──────────────────────────────────────────────────────────────────┐
│ 用户点「准备结束会议」                                               │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ 系统列出所有缺口，分两类                                             │
│ - 🚧 阻塞会议结束：必须完成的目标未覆盖 / 决策未拍板 / 行动项缺 owner │
│ - 📌 可会后跟进：讨论过但未确认、建议类目标未覆盖                    │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ 每个阻塞项三种处理                                                   │
│ 1) 转为行动项（带 owner + 截止，进入会后任务）                      │
│ 2) 记录例外原因（如「已知风险，本次不解决」）                        │
│ 3) 返回继续讨论（留在会议中，看板继续追踪）                          │
│ 支持「全部转为行动项」一键操作                                       │
└──────────────────────────────────────────────────────────────────┘
```

用户逻辑

- 缺口检查在「结束会议」动作前强制出现，不能直接关掉会议。
- 阻塞项不处理完，不能进入总结；可会后跟进项允许带出会议。

后台需要做什么

- 缺口由规则引擎依据目标优先级 + 覆盖状态推导；阻塞判定可配置（必须完成未覆盖 = 阻塞）。
- 转出的行动项写入会议对象，进入总结的「行动项」段落。

业务意义

这是工具价值落点：确保会议「关门前」把未决事项显式处理，而不是留在沉默里。

## User Flow 5：会议总结与导出

```Plain Text
┌──────────────────────────────────────────────────────────────────┐
│ 缺口处理完成后 → 自动生成六段式总结                                  │
│ 一、原会议目标  二、已达成的结论  三、决策事项                        │
│ 四、行动项(owner/截止)  五、未解决的问题  六、保留的风险与例外        │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────┐
│ 导出：复制全文 / 下载 Markdown                                       │
└──────────────────────────────────────────────────────────────────┘
```

用户逻辑

- 总结直接对应会前目标与结束前缺口，不编造未提及的结论（缺失只报告缺失）。
- 可下载为 Markdown，方便贴进文档或任务系统。

后台需要做什么

- 总结由前端根据会议对象纯函数生成（`lib/engine.ts` 的 `buildSummary`），无服务端依赖。

业务意义

把「目标 → 讨论 → 缺口 → 结论 / 行动」闭环成一份可分享的产物。

## User Flow 6：可选 AI 语义复核

```Plain Text
┌──────────────────────────────────────────────────────────────────┐
│ 会中页点「AI 语义复核」                                              │
│    │ 服务端已配 AI_API_KEY → 直接调用                                │
│    │ 未配 → 页面「模型设置」可临时自填任意 OpenAI 兼容 Key            │
│    ▼                                                                │
│ POST /api/ai-check → 返回每项目标的状态 + 理由                       │
│    │ 调用失败 / 无 Key → 降级，仍显示规则引擎结论                    │
└──────────────────────────────────────────────────────────────────┘
```

用户看到什么

- 配置 Key 后，覆盖看板每项多一个 `AI` 徽章，显示模型对达成状态的判断。

后台需要做什么

- `/api/ai-check/route.ts`：优先用请求自带 Key，其次用服务端环境变量 `AI_API_KEY` / `AI_BASE_URL` / `AI_MODEL`（默认 DeepSeek）。
- 失败降级：不阻断主流程，仅提示。

业务意义

规则引擎保证「没 Key 也能用」，AI 作为增强层提升语义判断准确率。

## 功能模块说明

### 会前配置

#### 会议目标

用户看到什么

- 四类目标（Key Goal / Conclusion / Decision / Action），每项目标有优先级。

后台需要做什么

- 目标结构写入会议对象；优先级驱动结束前缺口的严重程度分级。

业务意义

目标是整套覆盖检查的锚点。

#### 议程与角色

用户逻辑

- 选录入模式；为每个环节指定必发言人；维护参会人名单。

后台需要做什么

- 议程与角色参与发言人矩阵判定；缺角色则相应缺口不计算。

业务意义

让「谁该说却没说」可量化。

### 会中覆盖检查（核心模块）

#### 覆盖看板

用户逻辑

- 四个视图（目标 / 议题 / 发言人 / 行动项）实时反映达成度。

后台需要做什么

- `lib/engine.ts` 的 `computeCoverage` 做确定性匹配；`lib/nlp.ts` 做 owner / 截止 / 决策信号抽取。

业务意义

实时把「未覆盖 / 未表态 / 未指派」暴露出来。

#### 会中提示

用户逻辑

- 红/黄提示引导主持人现场追问。

后台需要做什么

- 依据缺失发言人与未拍板决策生成 nudge 文案。

### 结束与总结

#### 缺口检查

用户逻辑

- 强制在结束前出现；阻塞项三种处理。

后台需要做什么

- 缺口推导 + 转行动项 / 记例外 / 返回讨论的状态流转。

#### 会议总结

用户逻辑

- 六段式导出。

后台需要做什么

- 纯函数生成，不调用模型。

### 可选 AI 复核

用户逻辑 / 后台

- 见 User Flow 6；未配置 Key 时全部功能照常。

## 平台内核心字段

> 本节回答「从会前到总结，全程沉淀哪些数据」。数据存浏览器 localStorage，不上传。

```Plain Text
会前配置
  - objectives[]：{ kind, text, priority }
  - agenda[]：{ name, mode, mustSpeakers[] }
  - participants[]：{ name, role }
        │
        ▼
会中录入
  - transcript[]：{ speaker, text, at }
        │
        ▼
覆盖计算（lib/engine.ts）
  - coverage：{ objectives, agenda, speakers, actions }
  - gaps[]：{ type: blocker|followup, ref, message }
        │
        ▼
结束处理
  - actionsOut[]：{ text, owner?, due?, fromGap }
  - exceptions[]：{ gapId, reason }
        │
        ▼
会议总结
  - summary：{ goals, conclusions, decisions, actions, open, risks }
```

## 第三方能力对接（AI）

仅「可选 AI 语义复核」需要大模型；其余全部本地完成。

- 环境变量：`AI_API_KEY`、`AI_BASE_URL`（默认 `https://api.deepseek.com/v1`）、`AI_MODEL`（默认 `deepseek-chat`）。
- 兼容任意 OpenAI Chat Completions 接口（DeepSeek / 通义 / Moonshot / OpenAI）。
- 未配置时：AI 复核按钮禁用并提示，规则版判定照常；**不阻断主流程**。

## 本地运行与部署

```bash
npm install
npm run dev      # http://localhost:3000
npm run build    # 生产构建校验
```

部署（Vercel）

1. 推送本仓库到 GitHub；
2. Vercel → Add New → Project → Import 本仓库；
3. Framework 自动识别为 Next.js，无需环境变量，直接 Deploy。

## 说明（Mock 与已知限制）

- 示例会议为**人工编写的 Mock 逐字稿**，用于演示判定；无真实语音转写或会议软件集成。
- 覆盖判定默认由**规则引擎**完成（关键词 + 信号词 + 发言人匹配），非大模型语义理解；规则会漏判语义等价表述。
- 数据保存在浏览器 localStorage，不上传、无账号体系；换设备或清缓存会丢失。
- AI 复核为可选增强，需自配 Key；未配时降级为规则版。
- 未来可接：真实会议转写 API、LLM 语义判定、日历与任务系统回填（行动项自动建 issue）。
